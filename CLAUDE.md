# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static, no-build website hosting 20 full TOEIC practice tests (10 from "Hacker Volume 2", 10 from "Hacker Volume 3"). There is no `package.json`, bundler, or test runner — every page pulls its CSS and grading/rendering logic from `assets/` (see below) and keeps only its own `questionsData` inline. The site is fully public — there is no login/auth, no backend, no database. (A Firebase-based login + admin/user-management system used to exist; it was removed, so `firebase-config.js`, `login.html`, `admin.html`, and `config.js` are gone. Don't reintroduce imports to those filenames.)

## Running / previewing

There is no build step. Serve the directory with any static file server and open in a browser, e.g.:

```
npx serve .
```

or just open the HTML files directly (module scripts and relative imports work fine via `file://` in most cases, but a local server avoids CORS/module-loading edge cases).

There are no lint or test commands configured in this repo.

## Architecture

**Practice test pages:**
- Each test lives directly at `Hacker{Vol2,Vol3}_Practice/TEST{NN}/` with `ListeningTest{NN}.html`, `ReadingTest{NN}.html`, an `audio/` folder (MP3 for the listening section), and an `image/` folder (question-set screenshots, e.g. `131-134.png` for RC Part 6/7 passages).
- Every page keeps only its `questionsData` (prompt, options, correct `answer` letter) inline in a `<script>` tag — there is no shared/external question data file per test, and this part is never extracted since it's genuinely unique per-test content, not duplicate code. The rendering/grading logic that used to sit in the same `<script>` tag now lives in `assets/js/` (see below) and is loaded via `<script src="../../assets/js/....js"></script>` right after it.
- `index.html` at the repo root is the landing/dashboard page linking out to all 20 tests' Listening/Reading pages — it has no auth check, anyone with the URL can use it. It links its own `assets/css/index.css` (its layout is dashboard-specific, not shared with the test pages) and its two `<div class="volume-section">` blocks carry `id="vol2"`/`id="vol3"` so the breadcrumb on test pages (see below) can deep-link back to the right section.
- No page in the repo has an inline `<style>` block anymore — every page, including `index.html`, links external CSS from `assets/css/`.
- `assets/css/` holds the CSS shared by every test page, linked with `<link rel="stylesheet" href="../../assets/css/....css">` (two levels up from `Hacker{Vol2,Vol3}_Practice/TEST{NN}/`). There are only two files, and every test page (Listening and Reading alike) links exactly one — `common.css`:
  - `common.css` — the full shared layout/theme for every test page (header, breadcrumb, part nav, bottom bar, score panel, `.audio-player` sizing, question cards, options, buttons, responsive rules, etc.), byte-for-byte identical across all 20 Listening and all 20 Reading pages. There used to be a separate `listening.css` for just the `.audio-player` rules; it was folded into `common.css` since `.audio-player` simply never matches anything on a Reading page (no such element exists in that DOM) — no harm in the selector being present, and it's one fewer `<link>`/HTTP request for the 20 Listening pages.
  - `index.css` — layout/theme for `index.html` only (dashboard grid, test cards); not linked from any test page, and deliberately kept separate from `common.css` — the two share no selectors (dashboard markup vs. test-page markup), so merging them would just make both pages load CSS they never use.
  - `assets/images/` is currently unused — there are no images shared across tests; every image referenced from a page's `questionsData` (`image/NN.png`, `image/131-134.png`, etc.) is question-specific and lives in that test's own `TEST{NN}/image/` folder, not here.
- If you ever need to change shared styling, edit `assets/css/common.css` once — it applies to all 40 test pages automatically, unlike the old inline-`<style>`-per-page setup.
- **Color scheme (shared across the whole site, including `index.html`):** no `linear-gradient` anywhere — everywhere the old design used `linear-gradient(135deg, #667eea, #764ba2)` (page background, `.header`, `.passage-divider` in `common.css`; page background and `.header` in `index.css`) now uses the flat color `#8c9eef` (a ~75%-tint of the brand blue `#667eea` toward white). Since `.header` text sits directly on that lighter background, `.header`'s text color was changed from white to a dark navy (`#1e2749`) to keep it readable (white-on-`#8c9eef` failed contrast, ~2.5:1; navy-on-`#8c9eef` is ~5.7:1) — don't revert `.header`'s text color to white without also darkening its background back down, or it'll be close to unreadable. Smaller accent uses of `#667eea` (buttons, borders, badges like `.question-number`, links) were intentionally left as the original, more saturated `#667eea` in both `common.css` and `index.css` — only the large background areas were lightened, to keep those accents legible/vivid. Keep `index.css` and `common.css` using the same two blues (`#8c9eef` backgrounds, `#667eea` accents, `#1e2749` on-light-blue text) so the dashboard and the test pages read as one visual system.
- **Breadcrumb / navigation:** every `ListeningTestNN.html`/`ReadingTestNN.html` has a `<nav class="breadcrumb">` right after `.header`, generated the same way on all 40 pages. It's a single `position: fixed; top: 0` bar (max-width 1200px, centered, matching `.container`'s width) laid out as a 3-column CSS grid (`grid-template-columns: 1fr auto 1fr`) so it stays visible while scrolling; `.header` scrolls normally and disappears underneath it. `body`'s `padding-top` in `common.css` reserves space for it so the header isn't hidden on initial load:
  - Left column (`.breadcrumb-trail`, `justify-self: start`): `🏠 Home` (→ `../../index.html`) › `Hacker Volume {2,3}` (→ `../../index.html#vol{2,3}`) › current `Test {NN} · {Listening,Reading}` (plain text, not a link).
  - **Center column (`.part-nav`, `justify-self: center`)** — the in-page jump links to each Part, one pill per entry in `questionsData.parts` (`<a href="#part-N">Part N</a>`). It's an empty `<div class="part-nav" id="partNav"></div>` in the static HTML, populated at runtime by `renderPartNav()` (added alongside `generateQuestions()` in both `assets/js/` files, called from the same init function right before `generateQuestions()`). `generateQuestions()` sets `id = 'part-' + part.partNumber` on each part's header div (the `.passage` div holding `<h2>Part N - Title</h2>`) so the links have something to jump to — Listening pages get 4 pills (Part 1-4), Reading pages get 3 (Part 5-7), purely driven by whatever parts exist in that test's `questionsData`, not hardcoded. `.passage[id^="part-"]` gets `scroll-margin-top` in `common.css` so clicking a pill doesn't leave the target's heading hidden under the fixed breadcrumb. `.part-nav:empty { display: none; }` collapses that grid column cleanly if `questionsData` somehow has no parts, rather than leaving a visible gap.
  - Right column (`.breadcrumb-nav`, `justify-self: end`): a link to the sibling page for the same test (Listening ⇄ Reading), plus `‹ Test {NN-1}` / `Test {NN+1} ›` links to the previous/next test **within the same volume** (omitted at the volume's first/last test — no wraparound, and prev/next never cross Vol2 ↔ Vol3).
  - **Mobile (`@media (max-width: 768px)` in `common.css`):** the breadcrumb grid collapses to a single column (`grid-template-columns: 1fr`), so trail / part pills / nav buttons stack as three centered rows instead of competing for horizontal space; `.bottom-bar` likewise switches to `flex-direction: column` (score panel row, then a full-width `.audio-player` row) instead of squeezing the audio scrubber down to near-nothing. `.breadcrumb-btn`/`.part-nav a`/`.reset-btn` get larger padding in this breakpoint for easier tapping. Because both fixed bars get taller once stacked, `body`'s `padding-top`/`padding-bottom` and `.passage[id^="part-"]`'s `scroll-margin-top` are **overridden with larger values inside the same media query** — these were tuned by actually measuring `.breadcrumb`/`.bottom-bar` `getBoundingClientRect().height` at a ~390px-wide viewport, not guessed, so if you resize any element in the mobile breakpoint, re-measure and update these three values together or content will end up hidden under the fixed bars.
  - This is generated, repetitive markup — if you add a new test or change the nav scheme, keep the same per-file link math (relative `../TEST{NN}/...` paths, `#vol2`/`#vol3` anchors) rather than hand-writing it inconsistently across files.
- **Bottom bar (score panel + audio player):** right after `.breadcrumb`, every test page has a `<div class="bottom-bar">` that is `position: fixed; bottom: 0` (same 1200px/centered sizing as the breadcrumb) — `body`'s `padding-bottom` in `common.css` reserves space for it. It replaces what used to be a separately-`sticky` score panel and a separately-fixed audio bar; now `.bottom-bar` alone owns the fixed positioning/background/border/shadow, and its children are plain flex items:
  - `.score-panel` (always present, `justify-content: space-between` on the parent keeps it flush left) — a single `.score-item` showing **Correct / Incorrect** as one compact `X`/`Y` value (green `<span class="correct">`, gray `<span class="score-sep">/</span>`, red `<span class="incorrect">` — same `#correctScore`/`#incorrectScore` element IDs the JS already targets, just spans instead of separate divs now), then a `.score-item` for **Progress** (`#totalScore`, e.g. `0/100`), then the **Reset Quiz** button. That left-to-right order (combined correct/incorrect → progress → reset) is deliberate — don't reorder without checking this note.
  - `.audio-player` (Listening pages only, sits to the right of `.score-panel` in the same bar) — just the native `<audio>` control, sized with `flex: 1 1 0; min-width: 0;` (`common.css`) so it stretches to fill whatever width `.score-panel` doesn't use — a longer scrubber is easier to seek within. `.score-panel` has `flex-shrink: 0` so it always keeps its natural compact width instead of being squeezed by the growing audio bar. Reading pages' `.bottom-bar` contains only `.score-panel` and is narrower as a result (the `.audio-player` rules in `common.css` simply never match, since no Reading page ever renders that element).
  - If you touch this markup, keep it in sync across all 40 pages the same way as the breadcrumb — same structure, only the per-test audio filename (Listening) and IDs' values differ.
- `assets/js/` holds the rendering/grading logic shared by test pages (loading `questionsData`, generating question HTML, `selectAnswer`/scoring, `resetQuiz`). There are only two files now — every Listening page links `listening.js`, every Reading page links `reading.js`, no exceptions:
  - `listening.js` — used by all 20 `ListeningTestNN.html` pages (byte-identical logic across all of them).
  - `reading.js` — used by all 20 `ReadingTestNN.html` pages (byte-identical logic across all of them). `HackerVol3_Practice/TEST01` and `TEST02` used to link their own dedicated files (`reading-vol3-test01.js`/`reading-vol3-test02.js`) because their original inline logic looked meaningfully different (different function names, a `confirm()`-gated reset, etc.). On closer inspection none of that divergence actually changed behavior for their real `questionsData` — the differing code paths (an unguarded `passage.text` render, a string-vs-object option check) only guarded against data shapes those two tests don't have — except one genuine, user-visible difference: TEST02's Reset Quiz showed a `confirm()` dialog. That was intentionally dropped so all 20 Reading pages behave identically; the two dedicated files were deleted. The one real data quirk worth knowing: TEST02's Part 5 `q.id` values are **numbers** (`101`), not the `"q101"` strings every other test uses — `reading.js` calls `String(q.id).replace('q', '')` (not a bare `.replace()`) specifically so it doesn't crash on that page.
  - Both files independently maintain a `correctCount`/`incorrectCount` running total, recomputed from a `Map` (`questionState`) in `recomputeScore()`. **`selectAnswer()`'s incorrect branch must call `questionState.set(questionId, false)`** — for a while it didn't (it only ever deleted a *previous* `false` entry, never *set* one), which meant picking a wrong answer never incremented "Incorrect" or "Progress" in the bottom bar, silently, on every test page, until it was fixed. If you touch `selectAnswer()`, keep that `.set(questionId, false)` in the incorrect branch (mirroring the correct branch's `.set(questionId, true)`) or this regresses.
  - Both files wrap each group of questions into a 2-column `<div class="question-grid">` instead of stacking them full-width, **unless any question in that specific group carries an `image`** — checked separately for each group with `.some(q => q.image)`. This applies at two levels in `generateQuestions()`: (1) a part's direct `part.questions` (Part 1/2 Listening, Part 5 Reading) — Part 2 and Part 5 don't have per-question images so they grid; (2) **each individual passage's** `passage.questions` (Listening Part 3/4, Reading Part 6/7) — even though the *passage* itself usually has an image/audio-graphic, that image is rendered once in the passage header, not per question, so the passage's own question group (e.g. "Questions 196-200") still grids into 2 columns below it. Each passage gets its own separate `question-grid` (not one grid spanning multiple passages), so odd counts (3 or 5 questions) just leave the last cell empty rather than misaligning across passages. The grid styling itself (`.question-grid`, incl. the `max-width: 700px` single-column fallback) lives in `common.css`. If you touch `generateQuestions()` in either file, keep both has-image checks (part-level and per-passage) and the same wrapper-`<div>`-vs-`container` branching in the other file, or the two pages will drift out of sync on this too.
  - Part 1 Listening (`listening.js` only — this is the one case where per-question `q.image` is actually set) instead gets a **left-image/right-content** layout: `questionDiv` gets a `with-image` class; its direct children are the `Question N` badge (`.question-number`, a plain sibling — deliberately *outside* the flex row, so it anchors to the top-left corner of the whole `.question-block` rather than the top of the content column) followed by a `.question-row` wrapping `.question-media` (the `<img>`) and `.question-content` (prompt, options, feedback), laid out `display: flex` in `common.css`. This is a *different* mechanism from `.question-grid` — it's a 2-column split *within one question card*, not multiple cards side by side — and `.question-row` falls back to a single stacked column below `600px` viewport width. If a future part ever needs both (per-question images *and* multiple cards per row), these two mechanisms compose fine since `.question-grid` only wraps whole `.question-block` elements and doesn't care about their internal layout.
  - The question-prompt `<p>` and the passage `<img>` in both files use the shared `.question-text` / `.passage-image` CSS classes (`common.css`) instead of repeating the same `style="..."` string in every generated element — if you need to change how question text or passage images look, edit those two rules once rather than find/replacing the inline style across files.

**When adding or editing a test:** the Listening/Reading HTML files for a given volume are structurally near-identical (same CSS via `common.css`, and the same JS logic via `listening.js`/`reading.js` — genuinely all 40 pages now, no exceptions) — when changing shared *behavior* (scoring, audio player, answer review), edit the relevant shared file in `assets/js/` and it applies everywhere that links it; only touch a page's inline `<script>` if you're changing that test's `questionsData`. To start a new test page, copy an existing well-formed `ListeningTestNN.html`/`ReadingTestNN.html` (it'll already link the shared CSS/JS) and replace its `questionsData`, audio, and images — there are no separate template files in this repo.
